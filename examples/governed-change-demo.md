# WM：受控变更与下游验证示例

这是可公开的实验示例，使用两个模拟数字，不依赖私有交易系统、服务器或业务数据。它复用实验中的 `wm change` 和已有维护证据评估器，没有另建执行框架。

## 运行

在包含 `src/workspace_metabolism/changes.py` 的 WM 源码目录中运行：

首次试用可以获取独立预览分支（在一个新的目录中）：

```powershell
git clone --branch codex/wm-governed-change-preview --single-branch https://github.com/metabolism-tools/workspace-metabolism.git wm-change-preview
cd wm-change-preview
python examples/governed_change_demo.py
```

已有该分支源码时，只需：

```powershell
python examples/governed_change_demo.py
```

只需当前 WM 的运行环境，无网络请求、模型调用或额外账户。所有修改发生在自动创建的临时目录中，正常退出后清除。输出是一份 JSON 报告；可在需要留存时自行重定向保存。当前示例依赖尚未正式发布的 `wm change` 开发代码，不能假定已安装的 WM 0.5.2 能运行它。

## 它实际验证什么

先固定“2 条记录、总和 18”的验收条件，再提出压缩 JSON 格式的修改。WM 将检查结果绑定到明确的修改内容；修改后，一个固定程序实际读取记录并保存计算结果，验证器重新读取保存的结果核对。检查结果继续绑定同一任务、修改摘要、输入、验收条件和代码版本。

| 场景 | 实际行为 | 报告结果 |
| --- | --- | --- |
| 等价修改 | 只压缩格式，计算仍为 18 | `declared_checks_passed` |
| 错误修改 | 格式合法，但把 11 改成 12；下游得到 19 | `checks_failed`，恢复原文件并重新计算验证为 18 |
| 缺少下游验证 | 修改已完成，消费者尚未运行 | `verification_pending` |

恢复后的错误场景仍记录为失败，并单独标记 `recovered=true`。它没有把失败重写成成功，也没有把缺少证据当成无需监督。

这体现了与单纯定时清理的区别：清理完成只是中间步骤；任务是否可接受取决于下游结果，失败后的恢复也必须验证。定时任务同样可以实现这些检查，我们提供的是可复用的治理组合和明确的证据边界，而不是声称定时任务做不到。

## 使用边界

- 示例中的自动确认只针对一次性模拟目录，不代表用户身份认证或生产批准。评估器始终返回 `authorizes_execution=false`。
- `real_workflow` 在这里表示消费者确实执行了这个模拟工作流；最外层 `synthetic=true`、`production_validated=false` 明确排除生产证据。不得把这份输出计入真实业务成功率。
- 这里只校验记录数和总和，不能证明每条记录、排序或其他业务语义均等价。正式接入必须由业务负责人定义相应验收条件。
- 哈希用于关联和检查内容，不证明证据来自可信身份；本地可写状态不是安全隔离区。
- 示例的失败恢复动作事先限定为恢复输入文件并重新生成派生结果，不适用于已经发送的通知、订单或其他不可撤销副作用。实际系统应先隔离输出，再决定发布、恢复或交由人判断。
- 所有场景合计是一次模拟演示；没有测量人工接管时间，不宣称节省人工或 Token。
- 临时目录正常清理不等于生产留存治理。正式版本仍需规定未解决变更、恢复副本和审计证据的容量上限与保留期限，不能直接自动清除恢复材料。
