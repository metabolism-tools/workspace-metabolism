# 循环让 Agent 一直跑，代谢让工作区一直活

AI 写代码像喷泉，但你的工作区没有排水系统。

最近一年，大家应该都感受到了：AI 写代码真的很爽，但写完代码之后的**工作区**越来越乱。废弃的实现方案、临时补丁、重复的依赖锁文件、测试桩、半途而废的重构……AI 每跑一轮，就留下一批「中间产物」。代码在增长，工作区膨胀得更快。时间一长，整个项目就像一个没人打理的堆肥场——而下一轮 AI 还得在堆肥场里干活。

这不是小事。上下文被污染、构建越来越慢、旧方案和新代码互相打架。**问题不在 AI 写代码，而在代码之外的那些东西没人管。**

## 传统做法，为什么都不太行

最常见的答案是：写个脚本，到点 `rm -rf`。这太粗暴了。AI 的下一轮迭代，可能恰恰需要那个看起来「已经废弃」的文件。删掉的不只是一个文件，还有它的来龙去脉——什么时候产生的、为什么被放弃、还能不能复用。这相当于把可能有营养的中间产物直接烧掉。

另一种做法是「什么都不删」，结果工作区持续腐烂；「每轮都从干净沙盒重来」，成本极高还把历史也扔了；「什么都往 git 里塞」，版本库变成另一个垃圾场。

**清理是必要的，但「直接删除」不是答案。**

还有人会说：那就让 Codex 定时清理呗。定时任务能回答「到点删」，但回答不了「什么值得留、删错了怎么办、谁动过什么」——规则活在对话里，删了没有回收区，跑了没有账本。代谢系统把这些都写进仓库：策略可评审，回收可回滚，每一步可审计。两者还能组合：cron、任务计划、CI 都可以定时跑 `wm`——调度器负责「什么时候」，策略文件负责「怎么删、删错了怎么撤销」。

## 一个更大的故事：AI 编程的三幕剧

第一幕（Prompt Engineering）：AI 会写。

第二幕（Context / Harness / Loop Engineering）：AI 能一直写——可靠地、自主地。

第三幕（Agentic Metabolic Engineering）：工作区扛不扛得住一直写？

Loop 时代把 AI 变成了工厂，代谢时代要管理工厂留下的东西。所以这个框架可以用一句话概括：

> **循环让 Agent 一直跑，代谢让工作区一直活。**

## 我的提议：智能体代谢工程（Agentic Metabolic Engineering）

用生物学的「代谢」来理解 AI 工作区：它不是一堆文件的静态存放处，而是一个有生命、有容量上限的系统，需要的是**消化**，而不是简单的**删除**。

它由四个阶段构成：

| 阶段 | 命令 | 做什么 |
| --- | --- | --- |
| 分解代谢 Catabolism | `wm audit` | 体检：扫描工作区，给废弃草稿、重复缓存、半成品贴上「营养标签」，只诊断不破坏 |
| 隔离消化 Sequestration | `wm clean` | 把确认过期的内容移入回收区，**绝不直接删除**——今天看着没用的，下一轮可能就用上了 |
| 校验 Verification | `wm verify` | 哈希链审计日志：每个文件何时产生、何时被移动，全程可追溯，篡改会被发现 |
| 合成再生 Anabolism | `wm rollback` | 当新的迭代发现旧方案其实更好时，把回收区的内容重新注入工作区——废料变成原料 |

整套机制的基石是**策略即代码**：一份 JSON 策略文件给每个路径分级（G1 永不触碰 / G2 保留 / G3 审批+引用检查 / G4 自动），工具只做策略允许的事，绝不多做。在这套机制里，人的角色不是清洁工，而是**策略作者**：决定什么值得留、留多久、谁可以碰。

说明一下：这个比喻不是我们发明的（「信息代谢」60 年代就有人提出，「代谢工程」是合成生物学的成熟学科）。我们做的是把这个比喻用到 AI 工作区治理这个具体场景，并给它一个可审计的工具。**我们认领的是框架，不是这几个字。**

## 它在 AI 工程栈里的位置

| 层级 | 范式 | 核心问题 |
| --- | --- | --- |
| L1 | Prompt Engineering | 怎么跟模型说话？ |
| L2 | Context Engineering | 给模型看什么？ |
| L3 | Harness Engineering | 怎么让 Agent 稳定可靠？ |
| L4 | Loop Engineering | 怎么让 Agent 自己持续跑下去？ |
| **L5** | **Agentic Metabolic Engineering** | **每一轮循环之后，工作区剩下了什么？** |

如果说 Harness 是 Agent 的骨架，Loop 是它的心跳，那么代谢系统就是它的**消化系统**。一个没有代谢的 Loop，是无限产出废物的系统；一个没有代谢的 Harness，是装满自身碎屑的笼子。

## 一个可复现的证据：30 轮循环，两个工作区

仓库里带了一个对照实验（`examples/metabolism_benchmark.py`）：两个一模一样的工作区，各跑 30 轮模拟 agent 循环，每轮留下 8 个副产物（草稿、补丁、锁文件、缓存、测试桩、调试输出），共 240 个。一个工作区每轮结束都执行 `wm clean --grades G4 --yes`，另一个什么都不做。

| | 有代谢 | 无代谢 |
| --- | --- | --- |
| 活动工作区文件 | 2 | 242 |
| 过期候选 | 0 | 240 |
| 下一轮 Agent 会看到 | 真正的代码 | 真正的代码 + 240 个副产物 |
| 审计耗时（3 次取最优） | 79.9 ms | 92.9 ms |

有代谢的一侧，240 个副产物都在回收区里（0.4 MB），每批都有编号；`wm verify` 显示 33 条审计日志，哈希链完好。当第 31 轮发现第一轮的草稿才是对的，`wm rollback <run_id>` 用约 83 ms 把它原样恢复，逐字节校验通过。

数字会随机器变化（`python examples/metabolism_benchmark.py` 可复现），结构不会：无代谢的工作区线性膨胀，有代谢的工作区保持平坦，而且每个副产物都还能找回来。

仓库里还存着 2026-08-16 的真实运行记录（`docs/publish/benchmark-run-20260816.json`），含工具版本、运行时间、脚本校验值，任何人可以对照复现。

## 代谢债与工作区腐烂

**代谢债（Metabolic Debt）**：无人管理的副产物累积成的代价——文件越堆越多、上下文被污染、旧实现和新实现互相打架。它之于工作区，正如技术债之于代码库。**工作区腐烂（Workspace Rot）** 就是代谢债违约的后果。腐烂的反面不是「空」，而是「对」——对的文件、对的时间、可验证的历史。
