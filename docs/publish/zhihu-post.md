AI 写代码像喷泉，但你的工作区没有排水系统。能力越强，草稿、缓存、废弃方案堆得越快。直接 `rm -rf` 会烧掉下一轮 AI 可能需要的中间产物；什么都不管，工作区会慢慢腐烂。

这篇文章想提出一种框架：**Agentic Metabolic Engineering（智能体代谢工程）**——把工作区当作一个有生命、有容量上限的系统来管理：检查、回收、验证、回滚，全部由一份策略文件说了算，每一步都留下防篡改的审计记录。它是 agentic 工程栈的 L5 层：每一轮循环结束后，副产物怎么办。

一句话概括：**循环让 Agent 一直跑，代谢让工作区一直活。**

配套工具 `workspace-metabolism` 已发布在 GitHub 和 PyPI（v0.1.1），零依赖，Windows / Linux / macOS 通用。

## 一、AI 写代码，工作区越长越乱

vibe coding 和 agentic 循环改变了工作区的样子：

1. AI 生成代码
2. 报错了
3. AI 修复
4. 新的依赖或脚本出现了
5. 上一个方案被放弃，但没被删除
6. 循环继续

结果：`archive/`、`deprecated/`、`test_drafts/`、`tmp/`、半成品重构、重复的锁文件，增长速度比代码本身还快。工作区变成了一个没有园丁的堆肥场——而下一轮 AI 还要在这个堆肥场里工作。

## 二、为什么「直接删掉」不够

最经典的答案是写一个清理脚本，然后 `rm -rf`。这是「自噬」：把可能有价值的中间产物连同它的来历一起烧掉了。AI 的下一轮循环可能恰好需要那个看起来已经死了的文件。

另一个极端是什么都进 git。Git 适合被跟踪的源码，但工作区的大部分副产物是未跟踪、高变动、非代码的东西：缓存、日志、草稿输出、一次性实验。把它们全部版本化，版本历史会变成垃圾填埋场。

两个极端都不对。我们需要的是「消化」，不是「删除」或「囤积」。

## 三、把工作区当成活的系统：四个阶段

代谢的隐喻并不新：「信息代谢」可以追溯到 1960 年代，「代谢工程」也是合成生物学里的成熟学科。我们提出的不是把 AI 用在生物代谢上，而是把这套隐喻用在 AI 工作区的生命周期治理上，并配一个可审计的工具。

| 阶段 | 命令 | 在 AI 工作区里是什么 |
| --- | --- | --- |
| 分解代谢（Catabolism） | `wm audit` | 只做体检：扫描并给候选文件贴标签。不下判断，只加营养标签。 |
| 隔离（Sequestration） | `wm clean` | 温和发酵：把确认过期的文件移进回收区。绝不 `rm -rf`。 |
| 验证（Verification） | `wm verify` | 生物检定：哈希链日志记录每个文件何时产生、何时移动；任何篡改都会被检测出来。 |
| 合成代谢（Anabolism） | `wm rollback` | 再吸收：当新一轮循环发现旧方案更好，回滚把材料重新注入工作区。废物变成原料。 |

## 四、L5：agentic 工程栈的第五层

一个有用的视角是把 agentic AI 看成分层的工程栈：

| 层 | 范式 | 核心问题 |
| --- | --- | --- |
| L1 | Prompt Engineering | 我们跟模型说什么？ |
| L2 | Context Engineering | 我们给模型读什么？ |
| L3 | Harness Engineering | 怎么让 agent 在生产环境里可靠？ |
| L4 | Loop Engineering | 怎么让 agent 自己跑起来？ |
| L5 | Agentic Metabolic Engineering | 每一轮循环之后，副产物怎么办？ |

没有代谢的 Loop，是无限产生废物的系统；没有代谢的 Harness，是堆满自己碎屑的笼子。代谢是 agentic 栈的「卫生层」，而它的合成代谢那一半（回滚）又让它不只是清理层，而是复用层。

把这段历史讲成一个更大的故事：第一幕（Prompt）是「AI 会写」，第二幕（Context / Harness / Loop）是「AI 能一直写」，第三幕（代谢）是「工作区扛得住一直写」。Loop 时代把 AI 变成了工厂，代谢时代管理工厂留下的东西。

实践中可以在每轮循环结束、下一轮计划开始之前，加一步「微代谢」（micro-metabolism）：问一句「刚产生的文件——保留、归档、回收，还是留给明天的消化？」每日 audit、每周 clean 的定时任务就是同一个问题的无人值守版本。

## 五、策略即代码：G1–G4

工具只做策略允许的事，不多不少。所有路径的规则写在一个 JSON 策略文件里（下面是简化示例）：

```json
{
  "version": 1,
  "never_clean": [".git", "README.md", "src"],
  "entries": [
    {"path": "logs", "grade": "G4", "cleanup": "auto", "retention_days": 30},
    {"path": "archive", "grade": "G3", "cleanup": "approve", "retention_days": 60},
    {"path": "**/__pycache__", "grade": "G4", "cleanup": "auto", "retention_days": 30}
  ]
}
```

- G1 永不触碰 / G2 保留 / G3 人工确认 + 引用检查 / G4 自动
- 支持保护窗口：例如交易时段或工作时间，标记为 protected 的条目绝不动手
- 没登记在策略文件里的路径，默认不处理

在这套机制里，人的角色不是清洁工，而是**策略作者**：决定什么值得留、留多久、谁可以碰。工具只是把策略落地的执行者。

## 六、安全模型：默认只读，可精确回滚

- `clean` 默认 dry-run，先给你看它会做什么
- G4 需要 `--yes`；G3 需要 `--approve` 和 `--approver`（留下审批记录）
- 每次移动都记录每个文件的 SHA-256；`rollback` 先校验再恢复，拒绝覆盖已存在的路径
- `purge` 是唯一真正删除的命令，而且只在回收区内、保留期过后
- 日志和回收区默认放在工作区外面：`git add .` 永远不会把审计日志扫进版本库

## 七、代谢债务与工作区腐烂

**代谢债务（Metabolic Debt）**：未管理的工作区副产物带来的累积拖累——文件越堆越多、上下文被污染、旧实现和新实现互相打架。它之于工作区，正如技术债之于代码库。

**工作区腐烂（Workspace Rot）**：代谢债务长期不还的失败模式——工作区乱到 agent 的性能和可靠性可测量地下降。腐烂的对立面不是「空」，而是「对」：对的文件、对的时间、可验证的历史。

## 八、怎么衡量

一次体检就是一行命令：

```bash
wm audit --json | jq '.summary.growth_mb, .summary.recycle_ratio_pct, .summary.journal_chain_ok'
```

四个指标组：增长（体积、文件数、增量）、回收（回收区占比）、可审计性（哈希链完整性）、治理（候选、未登记路径、磁盘告警）。首次 audit 还没有基线，`growth_mb` 会是 `null`。

## 九、证据：30 轮循环，两个工作区

仓库里带了一个对照实验（`examples/metabolism_benchmark.py`）：两个一模一样的工作区，各跑 30 轮模拟 agent 循环，每轮留下 8 个副产物（草稿、补丁、锁文件、缓存、测试桩、调试输出），共 240 个。一个工作区每轮结束都执行 `wm clean --grades G4 --yes`，另一个什么都不做。

| | 有代谢 | 无代谢 |
| --- | --- | --- |
| 活动工作区文件 | 2 | 242 |
| 过期候选 | 0 | 240 |
| 下一轮 Agent 会看到 | 真正的代码 | 真正的代码 + 240 个副产物 |
| 审计耗时（3 次取最优） | 79.9 ms | 92.9 ms |

有代谢的一侧，240 个副产物都在回收区里（0.4 MB），每批都有编号；`wm verify` 显示 33 条审计日志，哈希链完好。当第 31 轮发现第一轮的草稿才是对的，`wm rollback <run_id>` 用约 83 ms 把它原样恢复，逐字节校验通过。

数字会随机器变化（用 `python examples/metabolism_benchmark.py` 可复现），结构不会：无代谢的工作区线性膨胀，有代谢的工作区保持平坦，而且每个副产物都还能找回来。

## 十、路线图与邀请

- 今天：CLI + 策略文件 + 定时任务
- 近期：agent 原生集成，让 agent 自己跑微代谢
- 中期：工作区健康分
- 远期：代谢策略成为像 `.gitignore` 一样常见的项目文件

最后是诚实声明：**框架是我们提的，词不是我们造的**。「信息代谢」可以追溯到 1960 年代，「代谢工程」是合成生物学已有的学科。我们提出的是把这套隐喻应用到 agent 工作区的生命周期治理上，并给出一个具体、可审计的工具。
