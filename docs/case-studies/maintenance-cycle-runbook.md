# 以低监督密度和下游正确性评价维护循环

本项目的核心工作假设：在人的既定目标和权限内，把执行、检查、维护、恢复和工作流接续做成可验证的循环，使人少承担重复检查、催办和纠错，更多承担目标、取舍和创造。监督收益可以独立成立，不要求同时节省Token或人工总时间。

本手册收窄并实施已有维护试点方案中的证据关联。它不另建harness或调度平台，也不宣称这种组合是首创。

## 当前工具分工与边界

| 部分 | 作用 | 本轮状态 |
|---|---|---|
| 领域执行器 + wm | 在已有权限内处理维护，保护研究证据、记录动作 | 已在实际系统使用；自动删字段关闭 |
| summarize_case_evidence.py | 检查wm日志链，汇总运行记录 | 已有工具；不证明业务恢复 |
| evaluate_maintenance_cycle.py | 将执行与检查绑定到同一任务、范围和版本，暴露缺失/过期/错配 | 新增只读评价器，按需运行；尚未接入生产调度或执行前拦截 |
| 现有人工监督记录工具 | 记录检查、纠正、催办及决策时间 | 沿用原型；本轮历史人工记录不完整 |
| 领域消费者 | 用维护后的成果完成下一段真实工作，并出具结果验收 | 每个场景单独接入；不能用心跳或执行器自报成功代替 |

评价器仅核对输入中声明的关系，不重新读取研究数据、不执行检查命令、不鉴别回执来源、不批准操作。伪造JSON仍可能通过声明检查，因此输出始终有`authorizes_execution=false`和`reported_not_authenticated`。现有执行器权限、锁和业务门禁继续生效。

## 衡量单位与顺序

**一个维护机会**是事先明确范围、触发条件和验收对象的一项工作，从触发记录到结果或待办。文件、重试、消息、检查步骤不另计机会。被拒绝、失败、等待和无收益均保留，不能只选成功任务。

1. 先核对后果边界：可能损害什么下游结果、如何发现、何时停止、谁决定、需要怎样恢复。
2. 再核对完成程度：动作执行、证据完整、真实消费者、恢复结果分别记录；失败与缺失不能相互覆盖。
3. 最后比较监督：同类任务、相同风险和相同验收范围下，每100次维护机会的监督会话数、监督分钟，同时报原始机会总数、失败数和未决数。缺失人工记录时不算零。
4. 同时列出必要决策/审核、人工总时间、Token、存储、计算和恢复成本，不合成一个可用空间收益抵消事故的总分。

连续成功不自动扩大权限；不能通过减少检查、缩小处理范围、把排障改名为“决策”、忽略失败或增加空转次数美化指标。

## 实操：从触发到下一轮工作

**开始前固定边界。** 写入cycle_id、对象清单摘要、策略/执行器/消费者版本，以及允许、暂停或需要人决策的选择。明确无响应时停止新增动作的范围，不能顺带停交易。恢复要求是领域规则的选择，不能由评价器根据空间大小猜测。

**执行期间复用原回执。** 执行绑定同一边界；处理量、异常、重试和实际结果由原执行器记录。对象或版本变化后重新约定，不能挪用旧检查。摘要不能替代必要原始证据。

**完成后关联检查。** 至少需要integrity（本范围的证据完整性）和consumer（下一段真实工作的领域验收）。需要实际恢复验收时增加recovery。每份检查必须有同一绑定、回执摘要、明确结果、检查时间和事前约定的有效期限；同名多份检查不自动挑好的一份。当前评价器要求这些结果出现在本轮执行结束后；执行前的恢复预案或演练另存，不冒充本轮恢复结果。

**检查不齐时保持待验证。** 明确失败返回checks_failed，缺失/错对象/过期返回verification_pending，全部声明检查通过才返回declared_checks_passed。预览、未执行、零改动分别显示，不能计作已完成实质维护。暂停边界下出现实际执行则显示boundary_violation。返回码0只代表声明检查通过，1表示未完成/失败/暂停，2表示输入无效；不是生产健康探针。

**记录人的介入。** 首次选择目标/范围记决策；为了让既定工作继续而催办、查日志、重复提示、纠错记监督。测量来源和本轮记录覆盖必须明确；只有coverage_complete=true、source=measured且计数有效时输出人工指标。即使记录了零分钟，也不证明比原流程改善。沿用已有注意力记录器，不另建一份重复台账。

**下一轮只带走必要材料。** 交付成果、边界、检查回执、未决项和有适用条件的失败经验。先在原调度中接入只读评价，核对误判后再另行考虑执行拦截；本轮没有接入自动执行或发消息。

## 用实际案例运行

在仓库根目录执行（只需Python标准库）：

```powershell
python tools/evaluate_maintenance_cycle.py docs/case-studies/evidence/matrix-maintenance-20260908.json --as-of 2026-09-08T13:27:42.785578+00:00
```

这是从云端原回执核验后提取的脱敏元数据，不含业务行、服务器地址、策略或账户。原始回执及各批回执哈希已重新核对；范围摘要覆盖279个不同对象。此处按新评价口径**回顾性整理一个案例**，不是事前冻结的对照实验，也不修改原有历史试验结论。

本次只按原完整性核查时点评估，valid_until等于该时点，不事后编造证据有效期。省略--as-of会按当前时间评估，历史检查可能过期；不能为得到绿色结果自动刷新检查时间。

预期返回码1：

```json
{
  "state": "verification_pending",
  "checks_passed": ["integrity"],
  "gaps": ["consumer:missing"],
  "supervision_minutes": null,
  "supervision_benefit": "not_established",
  "authorizes_execution": false
}
```

存储收益66.43 GB、279份引用和60个共享块的完整性均已有实际证据。这里缺的是**下一段真实研究任务使用这些成果后的验收回执**，不是否定已有字节还原与读取校验。人工记录也不完整，所以无法声称整个循环已达到低监督密度。

## 下一轮怎样形成可比较证据

首批只继续同类研究证据维护，不扩大到交易动作。由原流程在触发时记录维护机会，领域消费者在下一次有效使用后补同一绑定的回执，执行者在发生实际人工介入时补现有监督记录。尚未发生的消费者运行继续等待，不能为完成试验造一个空任务。

在下一轮开始前固定任务单位、范围、检查清单、有效期、资源预算、停止条件和观察窗口。将原流程与新流程的失败、漏报、复发、必要接管和总监督时间并列；没有可比基线，只报告当轮观察，不算改善百分比。5个周期是复盘点，不是统计证明；279份文件只属于这一项维护机会。

可被推翻的主张：在相同后果边界内，补足证据关联和消费者验收后，人的监督负担下降，同时下游错误不增加。增加记录但未减少接管、漏掉真实错误、正常任务被大量误拦、恢复仍需人反复定位，均属于反例，必须保留。

## 数据与隐私

评价输入上限1MiB，输出不包含传入的身份、路径或异常正文，不读取输入中指定的回执路径。实际回执真实性及领域验收由可信采集入口负责。公开案例只保留一个版本化小型脱敏输入，目标不超过16KiB；修订更新同一案例，不按每次轮询生成文件。真实证据继续留在原业务系统受保护的位置，沿用既有容量及保留规则。本轮不新增云端周期产物。
