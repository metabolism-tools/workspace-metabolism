# 当维护系统自身停摆：从执行记录到应执行事项

状态：根据自用系统事故整理的脱敏工程案例，附独立合成复现。不是公开可审计的生产数据集，也不是监督收益实验。

## 实际问题

维护入口新增了项目内导入，但定时任务通过脚本路径启动时未建立对应的导入环境，导致入口在写入运行证据之前失败。旧报告仍被两个下游界面或流程显示为最新报告，读取方没有检查新鲜度。任务是否完成与报告是否存在被混为一谈。

私有运行记录显示约 11 天的报告空窗；实际任务状态、入口复现和报告缺口共同支持故障判断。不能仅从空窗推断每一次历史触发都发生了完全相同的错误，也不能把期间不存在的调度次数算作失败次数。

后续核验还发现了部署路径问题：发布新版本不保证任务使用新版本，调度器可能继续调用旧副本；现有参数也可能与实际入口不匹配。这类问题应从实际运行路径验收。

## 在自用系统里做了什么

- 通过已有独立巡检对照应完成的时间窗口，识别缺失或过期的维护证据。
- 为固定动作保留有界的最新回执，并校验报告与执行产物的对应关系；界面不再仅凭旧报告文件名表示健康。
- 统一实际部署入口与持久数据位置，保留现有清理权限和周期。
- 复用已有通知路径，失败可重试，同一未解决事项去重。通知发送与故障解决分别记录。

已有人工触发的真实任务、产物核验及实际通知发送/重复抑制证据。它们支持“这条运行路径已验收”，不等同于自然调度的持续可靠性。无回执的历史清理或清除任务保持未知；没有为填补证据而提前执行清理。

这些运行功能属于自用系统适配代码，不是 WM 发布版已经提供的调度或通知能力。公开材料不携带服务器位置、账户、策略、凭据、私有路径或原始业务数据。原始证据留在私有事故记录，外部读者只能复现下述机制，不能据此独立认证生产结论。

## 沉淀到开源项目的改进

| 暴露的缺口 | 本轮公开源码改进 | 边界 |
| --- | --- | --- |
| 未启动的工作不在成功日志里 | 技能要求先识别应执行事项、观察起点和截止时间 | 仍由现有调度器或业务契约定义义务 |
| 旧报告继续代表健康 | 操作手册区分时间、对象匹配和真实消费者验收 | 哈希和回执不自行认证来源 |
| 恢复文件被当作恢复业务 | 可运行例子实际展示恢复字节后结果仍错误 | 合成数据，未对生产注入故障 |
| 告警次数被当作监督负担 | 评价表分别记录漏报、失败重试、重复、必要接管 | 未测量项目带来的人工或 token 节省 |
| 人工跑通被当作自动运行 | 记录实际触发来源、部署入口和待观察窗口 | `auto` 参数不证明自然触发 |

## 如何继续验证价值

使用[观察记录表](../../skills/metabolic-maintenance/references/observation-record.md)，从观察机制启用时间开始统计所有同类到期事项，包括遗漏、迟到、失败和无变更。自然事件与故障注入分开；历史未布置观察的区间不补造成功或失败。

记录遗漏发现时间、旧状态被显示为健康的时间、人工检查/修复分钟、下游通过/失败/缺失和通知覆盖。业务决策时间分列。对照应是具备合理心跳、备份、重试和验收的普通维护脚本，而非故意缺少保护的脚本。

可证伪的研究问题：在同类维护任务和相同验收要求下，把应执行事项与执行、恢复、消费者证据关联起来，能否减少必要人工接管，同时不增加遗漏或下游错误？如果普通脚本以相当成本做到同样结果，额外机制的收益尚未建立。

心跳、时效检查、重试和事件去重都有既有工程基础。本案例不声称发明这些机制、建立新的范式或证明学术及商业价值。当前贡献是一个具体故障来源、一组可复现的反例，以及可继续收集对照证据的操作方法。
