# 案例：声明了保留策略，却没有任何执行者（工作区外的临时目录）

- 案例编号：WM-RETENTION-001。
- 日期：2026-09-21；首次记录。**同一根因 2026-09-19 已被记录过一次**，两天后复发——本案例按"复发"登记，并记录上次为什么没解决。
- 范围：wm 直接行为（工作区外的临时目录既没有被核算、也没有被执行清理）＋ 相关系统经验（入口隔离优于逐点修补）。被维护对象是一个长期运行的自动量化研究工作区，固定时点跑维护与数据任务。
- 状态：止血与"真实执行者"已完成并验证；源头隔离已提交到主干，**尚未发布生效**。
- 结论：**"声明了保留策略"不等于"有人执行"**；而**磁盘告警本身并没有失效**——失效的是**归因**与**执行者**。这两点必须分开记，否则会把一次记账缺口误记成监控失灵。

## 问题与任务边界

该系统有一套"新陈代谢"记账：工作区内的目录被分级（永不清理 / 自动清理 / 需审批 / 可清理），每日跑一次只读体检，输出占用、增长与可清理候选；工作区之外的目录因为工具只接受相对路径，写不进分级表，只能另立一段"工作区外"声明其保留规则。

触发来自使用者的观察："**测量盲区这个在周末出现了大问题**"。要求先查清、再彻底修、最后写成案例。任务边界：只处理宿主机的临时目录与记账边界；不触碰交易、账户、风控、策略判据；不改任何清理工具的保护级别。

允许的动作：只读核查、定向回收明显弃用的副本、安装一个**幂等的**保留执行者、把台账声明改成可执行口径、给两个运行入口做临时目录隔离。发布不在授权内（需要另走发布流程与门禁）。

## 为什么它会累积：工作区外的"只核算"

工作区外的临时目录在体检报告里只有一行，形如"某目录 → 至少 X GB（扫描超时或部分路径不可读）（仅核算，按独立保留规则处理）"。而"独立保留规则"在台账里的原文是：保留期**依赖操作系统自带的临时目录清理机制（30 天）**，执行者写成该机制的系统定时器。

实测这句话**不成立**：那个系统定时器并不管辖本项目产生的目录（不是它创建、也不是它声明的路径），30 天对"按天产生的临时副本"也毫无意义。于是形成一种最容易被忽略的状态：**报告有数字、台账有规则、但没有任何东西会真的删除它们**。

它的量级（脱敏后的实测）：

| 时间 | 观测 |
| --- | --- |
| 首次记录（T−2 日） | 该临时根 **148 GB**，其中单个"整份工作区副本"占 **117 GB**；台账 evidence 字段留了证 |
| 复发复查（T 日） | 又长回 **69 GB**：同一类副本 **52 GB**（三天前建立、60 万+ 个文件、逐 inode 真副本而非硬链接、无进程/工作目录/打开句柄引用、未在任何分级表登记）＋ 9 个**由 root 创建**的部署追踪日志 2 GB |
| 清理一次之后按 root 视角复核 | 仍 **27 GB / 9.8 万项**：前缀为部署工具的 805 项 17 GB、通用临时目录 `tmp*` 6.9 万项 3.3 GB、若干按工具命名的小前缀若干千项 |

## 根本原因：两个入口一直在"撒"

逐点归因（对源码里创建临时目录的调用做统计）指向一个与直觉相反的结论：

- **不是**（如最初推测）少数后台任务忘了清理；
- **是测试与工具的运行入口本身**：被维护系统的测试文件里有 **127 处**用"创建临时目录"的原语，且**每次发布都会跑全量测试**（一天多次）。于是每个测试文件自己的临时目录前缀，正好对应临时根里成千上万个条目——`tmp*` 6.9 万项就是测试运行自身留下的。

再加上一层**权限事实**：这些目录**多由 root 身份的部署/维护任务创建**，而运行维护的用户**没有 sudo**；临时根又是 sticky 位（只有文件属主或 root 能删）。所以"把清理写进普通用户的定时任务"这条路**从一开始就不可能生效**——我第一版就是这么写的，它在真实环境里只会静默失败。这一点是本次最值得记的教训：**执行者放在哪一层，由权限决定，不由方便决定。**

## 实际过程（含失败与人工接管）

1. **先验证再删**（弃用副本）：确认无进程、无工作目录、无打开句柄引用；确认是逐 inode 真副本而非硬链接（否则删了不释放空间）；确认原工作区里的原件完好；确认该路径未在任何分级表登记。→ 回收 52 GB。
2. **清理 root 属主的残留**：用具备权限的身份删除 9 个部署追踪日志（2 GB）。
3. **装真实执行者**：把"清理工作区外临时目录"作为**第二个受管行**加进一个既有的、幂等的 root 级定时安装脚本（不新建平行机制），每日一次、**保留 2 天**、显式排除"一次性证据包"（那类东西必须人工核验正式原件后才决定）。安装脚本原本在"已存在"时提前退出，为容纳第二行改为"逐行判存在、只在有变化时写回"。
4. **把台账声明改成可执行**：该段落的保留期/执行者/证据改为"谁执行、跑什么命令、日志在哪、上一次实测数字"，并**保留被证伪的旧声明**及证伪依据（不抹去历史）。
5. **彻底修：入口隔离**（改两处，而不是改 127 处）：
   - 发布测试入口：每次运行创建一个隔离临时根，把 `TMPDIR/TMP/TEMP` 指给它，跑完在 `finally` 里整体删除；
   - 所有定时/手工工具的统一派发脚本：同上，加 `trap … EXIT/INT/TERM`；**并去掉该脚本原有的 `exec`**——`exec` 会替换进程，EXIT trap 不会触发（这是本次第二个"看不见的坑"）。
6. **失败与人工接管**：尝试把修复**当场发布**未成功——本地工作副本与远端主干已分叉（另有并行会话在同一工作副本里提交），而"从主干拉一个独立工作树打包"在本机遇到 Windows 路径与容器内路径不兼容（构建报"不是 git 仓库"）。**拒绝**用分叉的本地副本打包（会把本地独有提交带进生产），改为让修复随下一次常规发布生效，并在发布登记的放弃记录里写明原因与验收方法。使用者共 3 次介入（要求复查 / 要求彻底修 / 要求写案例），均为决策，不是被迫检查。

## 证据与可复核范围

- **记账侧**：维护工具在前一日报告"工作区增长 +1.9 MB"，而同一时段整机已用空间增加约 11 GB → 差额必然在工作区之外；次日报告首次列出工作区外临时根"至少 85 GB（扫描超时）"。**这两条放在一起才能说明"盲区"是什么**：探测没失灵，归因缺失。
- **量的证据**：上表三行（148 GB / 69 GB / 27 GB 与 9.8 万项），来源为体检报告、清理前后两次空间统计与按前缀归并的条目计数。
- **修复的验证**：本地与真实环境各跑同一小段测试：运行日志出现"临时根隔离：TMPDIR=…"，用例全通过，运行后隔离目录计数为 **0**；真实环境跑前/跑后临时根条目数 **19,189 → 19,189**（`tmp*` 8,605 → 8,605，零增长），隔离前缀残留 **0**——**连测试框架自己的基线临时目录也被圈进隔离根一并清掉**，这是"隔离确实生效"的直接证据。
- **总量变化**：整机已用从 **79% → 58%**（可用空间 66 GB → 129 GB）；临时根 69 GB → 18 GB。
- 本案例不引用任何私有路径、服务器地址、账户或策略字段；所有数字为容量与计数，原始回执保留在被维护系统的受保护位置。

## 结果、成本与局限

- **有效动作**：定向回收 2 次（52 GB + 2 GB）、保留机制首跑 1 次（约 9 GB）、入口隔离 2 处。
- **失败**：发布尝试 1 次（打包路径不兼容 + 主干分叉），未强推。
- **代价**：无额外网络与算力成本（全部在被维护侧执行，本地零下载）；未跑全量测试（随发布批次跑）。人工工时与 Token **未测**——本案例不据此宣称监督密度或成本下降。
- **局限（必须与结论一起读）**：
  1. 临时根本次**没有清零**（仍 18 GB：近两日部署包与按规则保留的一次性证据包），只是回到受控区间；
  2. 那 127 处调用**没有逐个改**——若将来有调用绕过这两个入口，仍会落在保留机制的兜底上；
  3. 部署脚本自身的追踪日志**仍缺 EXIT 清理**（该文件当时被另一并行会话占用），当前靠 2 天保留兜底；
  4. 隔离修复**尚未发布生效**，因此"下一次发布不再增长"仍是待验收项，不是已得结论；
  5. 不能宣称"工作区外已被记账体系覆盖"——只多了一条**受管的保留行**。

## 可复用机制与下一次验证

**可复用的机制**（与已有做法的差异）：

1. **把"保留声明"和"执行者"绑成一个字段**，并且该字段要**可被实测证伪**：写清谁执行、跑什么、日志在哪、上次回收多少。凡是只写"依赖某个系统机制"的声明，都应当被要求给出一次真实回执。
2. **清理的执行层级由权限决定**：创建者在 root、临时根又是 sticky 位时，非特权用户的清理任务是**结构性无效**的；应在设计阶段就问"谁有能力删"。
3. **对"满地小临时目录"，优先入口隔离而非逐点修补**：改两个入口（测试入口 + 工具派发入口）即覆盖成百处调用点；代价是必须知道 `exec` 会吞掉 EXIT trap 这类语言/运行时细节。
4. **半成品要如实记为半成品**：上次（T−2 日）已经"发现并登记"，但没有执行者——正是"登记了就等于做了"的错觉让它在两天后复发。

**下一次验证**（可推翻本案例的支持性结论）：

- 发布生效后核对：两个入口脚本中确实含隔离逻辑；随后**每次发布**观察临时根条目数是否**不再单调增长**；保留执行者的日志在预定时间有输出且回收字节数 > 0。
- 若一个月内条目数仍随发布单调增长 → 说明有调用绕过两个入口，须回到生成侧逐个加清理，并重新评估"入口隔离足够"这一结论。
- 若整机已用空间在无人工介入下再次回到告警线附近 → 说明保留规则不足以覆盖真实产生速率，需要按产生量而非按天数设定保留。
