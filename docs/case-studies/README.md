# 从运行案例积累价值

wm 的研究从实际维护任务开始。先证明系统做得更稳、人的监督负担是否下降，再讨论独特性、学术和商业价值。运行时长、告警变少、回收字节数都不能独立证明成功。

## 每次怎样记录

1. 维护或修复任务完成时，由执行者按 [案例模板](case-template.md) 留一份小型记录；正常运行复用原有回执，不每天生成一篇文章。
2. 新故障、复发、人工接管、清理后下游失败、没有收益的实验均须记录。同一根因更新原案例，不把重复告警算成多个独立案例。
3. 原始证据保留在业务系统受保护的位置；案例只引用版本、时间、范围及校验值。不能用摘要替代必要的审计依据，也不能无限复制日志。
4. 执行者在完成工作时复核结果；涉及业务决策时交给人。未知项明确填“未测”，不为了填表持续打扰人。
5. 每累计 5 个独立案例，或发现旧结论被反例推翻时，做一次小结。先使用已知文献与项目比较；只有形成可检验的新主张且需要发布时，才针对该主张核查先例。

这是执行手册，尚未增加自动采集器或新的定时任务。历史案例缺失的数据不追溯编造。

## 统一评价口径

| 评价 | 记录方式与限制 |
|---|---|
| 人工监督 | 检查、纠正、重新提示次数及分钟数；与人的业务决策、创造工作分别记录，无法区分时标未知 |
| 监督密度 | 每 100 次同类、同风险的有效任务需要多少次人工接管及多少监督分钟；同时报告总任务数、总人工时间和失败数，避免增加空转稀释指标 |
| 自主性 | 在明确权限和资源范围内，从委托到验收的无人介入区间；等待时间与实际执行时间分列，不能用跑得久代替完成得好 |
| 可靠性 | 下游验收通过率、复发、漏报、错误放行及证据覆盖；无样本、监控缺失不计成功，隔离测试与线上结果分开 |
| 总成本 | 已验收任务的计算/Token、人工监督、存储、备份、重试及恢复成本；失败任务成本也计入。没有完整计量就不宣称省钱或省 Token |
| 注意力价值 | 减少了哪些被迫检查、连续工作是否少被打断；须有记录或用户反馈，不能把估算分钟直接当成已实现收入 |

比较必须说明任务难度、数据量、运行窗口和其他同期改动。以原有流程为基线；危险操作只在隔离副本比较，不为研究故意削弱生产保护。短期改善不能证明长期可靠性。

## 价值如何升级为证据

- **工程价值**：真实缺陷可复现，修复有回归，下游结果可验证。
- **独特性与创新性**：找到已有工具未满足的具体需要，说明与现有方法的重合和差异；组合已有技术本身不证明首创。
- **学术价值**：提出可被反例推翻的问题，有对照、失败案例和可脱敏复现材料；多案例支持才考虑一般化。
- **商业价值**：区分用户痛点、使用意愿、付费意愿与实际收入。自己的系统有效不等于外部客户愿意购买。

当前最值得检验的问题：**维护在减少存储与运行负担时，怎样保留下游判断、排除重复失败及验收恢复所需的证据，从而减少人工接管？** 引用保护、负缓存、生命周期管理已有先例；这里暂列研究问题，不宣称新范式。

业务系统的对账交接修复与证据缺失检查先留在私有记录中。它们可启发 wm 的验收设计，但不能算作 wm 已实现的功能或 wm 直接修复的事故。

对外材料须去除账户、订单、策略、服务器位置、凭据和私有证据链接；用独立的合成样本复现机制，并明确它不是线上收益证据。
